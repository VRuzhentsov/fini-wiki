# Quest

Actionable unit shown to the user right now. In repeating flows, this is an occurrence-level record (see [[QuestSeries]] and [[QuestOccurrence]]) [[sources/2026-03-21-mvp-baseline]] [[sources/2026-03-22-mcp-contract-baseline]]. In the current implementation, quest persistence is carried directly by the Diesel-backed Rust model layer rather than a separate repository abstraction [[sources/2026-04-12-fini-current-data-layer]].

## Fields

These fields combine the MVP product baseline with the first structured MCP contract shape [[sources/2026-03-21-mvp-baseline]] [[sources/2026-03-22-mcp-contract-baseline]].

The live backend confirms that this is not just a design target: Diesel models and schema currently persist quest ids as text and default `space_id` to `"1"` in Rust and SQLite [[sources/2026-04-12-fini-current-data-layer]].

| Field | Type | Default | Description |
|---|---|---|---|
| `id` | uuid string | — | Primary identifier for the quest record |
| `series_id` | uuid string \| null | null | Parent [[QuestSeries]] when this quest is generated by recurrence |
| `space_id` | string | `"1"` | Parent [[Space]] id (`"1"`, `"2"`, `"3"`, or UUID); never null |
| `title` | string | — | Primary quest label |
| `description` | string \| null | null | Optional details |
| `status` | enum | `active` | See [Status](#status) |
| `priority` | enum | `none` | See [Priority](#priority) |
| `energy` | enum | `medium` | Stored for post-MVP behavior; hidden in MVP UI |
| `due` | date \| null | null | User-facing due date |
| `due_time` | time \| null | null | Optional user-facing time |
| `due_at_utc` | datetime \| null | null | Stored UTC cache used by current implementation; under the reminder bridge, wall-clock due fields remain the source of truth for notification scheduling |
| `repeat_rule` | RepeatRule \| null | null | Recurrence settings; see [[RepeatRule]] |
| `order_rank` | float | `0` | Ordering rank in signed range `-100..100` (lower first) |
| `completed_at` | datetime \| null | null | Set on completion |
| `created_at` | datetime | — | Creation timestamp |
| `updated_at` | datetime | — | Last update timestamp |

## Status

Status remains the main split between backlog-eligible quests and history entries [[sources/2026-03-21-mvp-baseline]].

| Value | Kind | Meaning |
|---|---|---|
| `active` | state | In backlog and eligible to become Focus |
| `completed` | terminal status | Done, shown in [[HistoryView]] |
| `abandoned` | terminal status | Intentionally dropped, shown in [[HistoryView]] |

## Focus quest selection

The core rule is that Focus/Main is derived from persisted state and events, not stored as a separate mutable singleton [[sources/2026-03-21-mvp-baseline]].

Focus quest is computed by getter from quest data/events, not from a separate mutable singleton state.

### Override signals

- Manual and reminder override events are written to [[FocusHistory]].
- Focus metadata is owner-scoped and does not live in quest rows.

For active quests, latest override timestamp wins. Reminder overrides are temporary preemption; when reminder-driven quest resolves, next most recent valid override is used [[sources/2026-03-21-mvp-baseline]].

### Fallback order

Fallback order was already locked in the original MVP baseline [[sources/2026-03-21-mvp-baseline]].

If no active override exists:

1. Overdue quests first
2. Lower `order_rank` first
3. Higher priority first
4. Oldest `created_at` first

## Ordering notes

`order_rank` is part of the model/API even though drag-and-drop UI is deferred [[sources/2026-03-21-mvp-baseline]].

- `order_rank` is currently model/API-level ordering metadata.
- Drag-and-drop rank editing in UI is deferred for now.

## Due and overdue semantics

The newer reminder bridge keeps `due` and `due_time` as the user-facing source of truth and derives reminder behavior from them in the backend [[sources/2026-04-24-reminder-due-bridge-grilling]].

- If `due` and `due_time` are set, the quest should notify exactly at that local wall-clock time.
- If `due` is set and `due_time` is null, the quest should notify at `09:00` local on that date.
- Backend `update_quest` owns the reminder bridge: quest due/state changes upsert or delete the derived [[Reminder]] row.
- The stored `due_at_utc` value is useful implementation data, but under the bridge it is not the authoritative scheduling source; UTC should be recomputed from local due fields when scheduling notifications.

## Restore

Restoring from history makes the quest active again and pushes it back into Focus selection [[sources/2026-03-21-mvp-baseline]].

Restoring from history sets `status = active` and appends a `restore` event in [[FocusHistory]] (restored quest becomes Focus immediately).
